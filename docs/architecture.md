# Knowmon architecture and design decisions

For the overall technology choices and principles, see `roadmap.md`. This document records the design decisions made during implementation.

## Where data lives

| Data                                                        | Location                                      | Rebuildable?                         |
| ----------------------------------------------------------- | --------------------------------------------- | ------------------------------------ |
| Notes                                                       | `<vault>/**/*.md`                             | Source of truth                      |
| Editing history                                             | `<vault>/.knowmon/events.jsonl` (append-only) | Source of truth                      |
| Index database                                              | `<vault>/.knowmon/index.db`                   | Fully rebuildable from the two above |
| Vault settings (time and semantic parameters)               | `<vault>/.knowmon/settings.json`              | Defaults used when missing           |
| App settings (last opened vault, Ollama address and models) | `userData/settings.json`                      | —                                    |

- `note_events` can't be recovered after the fact, so SQLite only holds an index and the truth is in `events.jsonl`. After the DB is deleted, reopening the vault replays the log (`replay` in `src/main/db/events-log.ts`).
- The log records paths, not note ids (ids change after a rebuild). Renames are written as `{"op":"rename"}` and deletions as `{"op":"delete"}`; on replay, history follows the path, and folder renames/deletions apply to every note under them.
- The schema version is stored in `PRAGMA user_version`. On a mismatch, the DB is deleted and rebuilt; no migrations are written.
- Files and folders starting with a dot (including `.knowmon`, `.obsidian`, `.git`) are not vault content: they aren't shown or watched, and IPC refuses to access them.

## Sync: reconcile

`Vault` (`src/main/vault/index.ts`) is the only place in the main process that touches files and the DB, and every operation runs in order through one queue.

- Folders aren't stored in the DB and have no events; `notes.createFolder` only creates an empty folder and notifies the renderer (added to the contract with the user's approval, 2026-10-06).
- Create/rename/delete/write inside the app: update the file, the DB and the log directly, and record the new mtime and hash immediately.
- External changes: chokidar only triggers (200 ms debounce); the actual differences come from `reconcile()`, which compares the disk with the `notes` table. If the mtime is unchanged the file isn't read; if the hash is unchanged it isn't an edit; a missing file whose hash matches a new file is treated as a rename, keeping its history.
- Watcher echoes from the app's own writes are skipped because the mtime already matches.
- Deletion moves files to the system trash through `shell.trashItem`.

## note_events rules

- `create`: created in the app, or a new file was found (using the file's birthtime; every note gets one the first time an existing vault is opened).
- `edit`: saved in the app, or reconcile found the content hash changed (using the mtime).
- `open`: `notes.read()`.
- For the same note and event kind, only one event is recorded per `EVENT_THROTTLE_MS` (60 seconds), so autosave doesn't flood the log. Sessions in phase 4 default to 30 minutes, so one-minute granularity is enough.

## Indexing, links, search (phase 2)

- The parser `src/main/indexer/parse.ts` is pure: `event_date` comes from frontmatter `date:`, otherwise from a `YYYY-MM-DD` prefix in the file name; wikilinks exclude frontmatter, fenced code and inline code; corrupt YAML is treated as no frontmatter.
- The title is always the file name (user decision, 2026-10-07); `title:` in the frontmatter is just an ordinary property.
- Wikilink resolution rules live in `src/shared/links.ts`, shared by main and renderer: case-insensitive, Unicode NFC; a target containing `/` matches the end of a path, otherwise the file name; on a clash the shortest path wins, then lexicographic order.
- `links` table: one row per (source, target) wikilink, with `weight` as the number of occurrences. A NULL `dst` means the target doesn't exist, with `target` keeping the original text. After a note is created, renamed or deleted, `relinkWikilinks` re-resolves every `dst` (without rereading files), so writing a link before creating the note still connects. Renaming doesn't rewrite `[[old name]]` in other notes.
- `notes_fts` (trigram, rowid = notes.id) stores the title and body. The body's frontmatter is replaced by the same number of blank lines so line numbers match the file; backlink context is read from here, not from disk. Deletes and renames are kept in sync by triggers.
- Incremental: when the content hash matches the DB, only the mtime is updated and nothing is re-parsed; renames force a re-parse (the date in the file name may change).
- Search: split on whitespace, all terms ANDed. Terms of 3+ characters use `MATCH` (bm25, title weight 10); shorter ones (common 2-character Chinese words) use `LIKE`. Notes whose titles contain every term come first. Snippets are extracted in main with JS and returned as `TextSegment[]`, so the renderer inserts no HTML.
- Renderer: "Files / Search" sidebar tabs (`Ctrl/Cmd+Shift+F`), the `Ctrl/Cmd+O` Quick switcher (fuzzy matching, recently opened first, kept in memory only), and a backlinks panel on the right. `Ctrl/Cmd+click` on a wikilink opens the note (add Shift for a new tab); if the target doesn't exist, it is created at the vault root. `[[` autocompletion uses `@codemirror/autocomplete` and inserts the shortest target that resolves uniquely.

## Graph (phase 3)

- Data: `graph.get()` returns every note and the resolved wikilinks (`src/main/db/graph.ts`); multiple rows for the same pair are merged with weights added, and self-links are excluded. Notes that don't exist yet aren't shown (user decision, 2026-10-07). The local graph is computed by the renderer with a BFS over the global data; no extra IPC.
- Drawing uses the Cytoscape canvas and layout uses `d3-force` in a Web Worker (`src/renderer/graph/layout.worker.ts`); Cytoscape's built-in `cose` and `fcose` take 10–37 seconds at 1000 notes and freeze the UI. Positions are sent back to the main thread as a `Float32Array` (transferable).
- Non-overlapping labels: the collision force uses a rectangle covering the node plus the label below it (`labelCollide.ts`; label width is estimated per character: one full width for CJK characters, about 0.6 for others), with one more collision-only pass after convergence. Cytoscape labels and nodes share a coordinate system and scale together, so labels that don't overlap in the layout don't overlap at any zoom level. To make room, repulsion is stronger, centering is weaker and repulsion distance is unlimited (measurements in `docs/plans/phase3-graph.md`).
- Above `LARGE_GRAPH` (500) nodes: the worker returns positions only once it converges (redrawing the whole Cytoscape canvas takes about 45 ms each time), and hover only highlights neighbors without fading the rest.
- Node positions are cached in the app's memory (one cache per vault, separately for the global and local graphs) and never written to disk. New nodes are placed next to neighbors that already have positions, and small changes only gently reheat the layout instead of redoing it.
- The global graph is a kind of tab (at most one). It stays mounted while the tab exists and is only hidden when you switch away, so switching back doesn't rebuild it.
- Cytoscape's WebGL renderer is experimental and broke click detection in testing, so it isn't used. Performance numbers and trade-offs are in `docs/plans/phase3-graph.md`.
- Colors come from CSS variables in `main.css` (`src/renderer/graph/style.ts`) and are reapplied when the theme changes. Preferences are stored in localStorage: `knowmon.graph.labels`, `knowmon.graph.depth`, `knowmon.sidePanel`.
- The right panel has two tabs, Backlinks and Local graph, which follow the current note tab; when the current tab is the graph, they show "no note open".

## Time layer (phase 4)

For concepts, rules and design reasoning, see `docs/time-layer.md`; for the plan and decisions, see `docs/plans/phase4-time.md`.

- The three kinds of time edges are derived by the pure functions in `src/main/indexer/timeLinks.ts` from `notes` and `note_events`, and written to the `links` table (`dst` is never NULL):
  - `same_session`: all `edit` events in the vault are sorted by time and split into a new session when the gap exceeds `sessionGapMinutes`; notes edited in the same session are all linked to each other, weighted by the number of shared sessions. Only `edit` counts (`create` is backfilled with the birthtime the first time a vault is opened, so many may share the same moment; `open` is just reading). A session that edits more than `sessionMaxNotes` notes is treated as a batch operation and produces no edges.
  - `same_day`: `event_date`s at most `sameDayWindowDays` apart, weighted `1 / (1 + days apart)`.
  - `sequence`: notes with an `event_date` in the same folder (including the root) are chained by date (by path within a day), earlier → later (user decision: "same topic" = same folder, 2026-10-08).
  - For undirected edges, the path that sorts first is the `src`.
- Time edges aren't incremental: a change to any event, date, path or setting can affect the whole vault. `Vault` marks them dirty on change, and `graph()` recomputes them in one batch before reading (1000 notes and 50,000 events within 500 ms; see `src/main/db/time.test.ts`). No schema change needed; on a DB rebuild they are recomputed after the events are replayed from the log.
- Session splitting (`sessionize`), date conversion, and parameter defaults and ranges live in `src/shared/time.ts`, shared by main and renderer; timeline sessions and `same_session` use the same function and parameters (the timeline also counts `create` in sessions).
- Time parameters are stored in the `time` field of the vault's `.knowmon/settings.json` (user decision, 2026-10-08); main clamps them with `clampTimeSettings`, and writes keep the file's other fields.
- `GraphNode.activeDays`: the local dates with `create` / `edit` events, used by the graph's "written time" filter. Dates always use the local time zone (`localDay`); main and renderer run on the same machine.
- Graph: `edgeId` includes the type (a pair of notes may have several kinds of edges). Edge-type filters affect layout (time edges take part in it too); toggling reuses the position cache and reheats gently. The time range filter only adds a `hidden` class to nodes (`display: none`) without re-running layout, throttled with `requestAnimationFrame`. Haystack edges don't support arrows, so the direction of `sequence` isn't drawn; multiple edge types between the same pair overlap on one line.
- Preferences (localStorage): `knowmon.graph.types`, `knowmon.graph.localTypes` (comma-separated, all on by default), `knowmon.graph.timeAxis`, `knowmon.graph.undated`, `knowmon.timeline.mode`. The time range itself isn't stored.
- The timeline is a kind of tab (`kind: 'timeline'`, at most one) and, like the graph, stays mounted while it exists; it doesn't refetch data while hidden. "Written" mode fetches all `create` / `edit` events at once (`timeline.activity`) and groups them in the renderer.

## LLM (phase 5)

For the plan and decisions, see `docs/plans/phase5-llm.md`. All Ollama calls live in `src/main/llm/`; Ollama is optional, and everything else works when it can't be reached.

- The Ollama client (`ollama.ts`) uses only Node's built-in `fetch`, and chat always sends `think: false` (so qwen3 doesn't output its reasoning; models that don't support it are retried without the parameter). Connection checks time out after 2 seconds and each embedding batch after 60 seconds; chat can be cancelled and has no timeout.
- `LlmService` (`service.ts`) manages connection state: it checks when a vault opens, when the user clicks Retry, and when embedding or a summary finds it offline; while offline it retries every 30 seconds. State is pushed to the renderer with `llm:statusChanged`. Settings (address, models) are stored in the app's `userData/settings.json`, shared by all vaults.
- Chunking (`indexer/chunk.ts`, pure): split into sections by heading and into paragraphs by blank lines, accumulating to about 800 characters; overlong paragraphs are split by sentence (an English period must be followed by whitespace, so 3.14 isn't split); fenced code is kept whole. Each chunk records its starting line and heading path, and the text sent for embedding is prefixed with "Title › Section".
- Schema version 3: `chunks` (`AUTOINCREMENT`, ids never reused) and `meta` (`embed_model`, `embed_dim`). Compared with the plan there is an extra `chunks.heading` column (needed for the embedding text). The vector tables `vec_chunks` and `vec_notes` (sqlite-vec `vec0`, cosine) are created on the first embedding, since the dimension depends on the model; deletes use triggers. Changing models drops both tables and recomputes.
- `indexFile` rewrites chunks when it re-parses; if the content is identical (for example a rename), the existing vectors are kept. It only touches the DB and never calls Ollama.
- `Embedder` calls Ollama in the background, 16 chunks per batch. **It doesn't go through the Vault queue**: better-sqlite3 is synchronous, so writes can't interleave with other operations; if a note is modified or deleted mid-embedding, its old chunks no longer exist (ids aren't reused) and `storeEmbeddings` skips them. A note's vector = the average of its normalized chunk vectors.
- Hybrid retrieval (`retrieve.ts`): full text (`searchNotes`) and vectors (`vec_chunks` KNN) each take their top 50 notes, merged with RRF (k = 60); the wikilink/semantic neighbors of the top 5 get half of the seed's score. Date filters use `event_date`, or the last modified date when there is none. When no query vector is available (offline, not built yet, different model), it falls back to full text + graph with `vector: false`.
- Semantic edges: the union of each note's 5 most similar notes (at or above the threshold), weighted by similarity. The default threshold is 0.65: with bge-m3 on test-vault, unrelated sentences score about 0.42 and related ones about 0.77, and 0.6 adds a few marginal edges (measurements in the plan). Per-note vec0 KNN takes 1.5 seconds at 1000 notes, so similarity is computed pairwise in JS instead (about 0.6 seconds), yielding the event loop about every 10 ms so the main process doesn't stall; that is why `Vault.graph()` became async. Like time edges, they are recomputed in one batch before the graph is read (marked dirty when note vectors, notes or settings change).
- Summaries (`summarize.ts`): bullet points that keep the original's wikilinks. The prompt includes the list of links in the original (`linkTargets`) and only those may be used; the prompt itself contains no `[[...]]` examples (small models copy examples verbatim into the summary). The output is filtered while streaming by `createLinkFilter`, which turns any `[[x]]` not in the original into plain `x`, deciding only at `]]` or a newline, so links split across chunks are handled. The language comes from `SummaryRequest.language` (`zh-TW` by default, or `en`; added to the contract with the user's approval, 2026-10-12), toggled by "中文 / EN" in the AI tab and stored in localStorage `knowmon.summary.language`. English mode repeats the language instruction after the content: qwen3:8b tends to answer Chinese notes in Chinese, and with Chinese examples in the prompt it even switches to Simplified Chinese. Beyond 12000 characters, the text is summarized in 6000-character parts first and then combined (part summaries aren't shown). The body comes from `notes_fts` (frontmatter already blanked out), so the renderer flushes autosave first. Streamed chunks are pushed with `llm:summary` and matched by request id in the renderer.
- Summaries are rendered as Markdown (`renderer/chat/parseMarkdown.ts`; originally `markdown.ts`, which differed from the `Markdown.tsx` component only in case and resolved to the wrong file on case-insensitive file systems on macOS/Windows, breaking the build, so it was renamed): the editor's lezer parser (GFM) plus a wikilink extension produces a simple tree that React turns into elements, without inserting HTML; external links only allow http(s) and mailto, and tables and HTML are shown as source.
- Renderer: an "AI" tab in the right panel (status, summary) and status at the bottom of the sidebar; the search panel toggles Keyword / Hybrid (`knowmon.search.mode`), Hybrid queries only on Enter, and clicking a result scrolls to the most relevant passage. When background embedding finishes (busy → false), `indexVersion` is incremented so the graph picks up new semantic edges.
- The stored format for graph edge-type preferences became "`a,-b`" (recording both on and off); new types not mentioned in the old format (semantic) default to on.

### Cloud chat providers (2026-11-20)

For the plan and decisions, see `docs/plans/cloud-providers.md`. User decisions: Ollama stays the default, and a cloud provider must be chosen explicitly with a consent checkbox (note content is sent to the provider); the cloud is **only for chat** (summaries, Q&A, Agent) and embeddings always use Ollama; the first version supports OpenAI, Gemini (OpenAI-compatible endpoint) and custom OpenAI-compatible APIs, not Claude; no new dependencies.

- `openai.ts`: `createOpenAiCompatible` uses only the built-in `fetch` and implements `ChatClient` (in `ollama.ts`; `OllamaClient` extends it with `version` and `embed`). It parses SSE and accumulates tool call `arguments` string fragments by `index`, parsing them only at the end. Internally, messages keep the Ollama format and are converted when sent (`toOpenAiMessages`). Errors use the same class (renamed `LlmError`, with `OllamaError` kept as an alias), adding `auth` (401/403) and `rate` (429). Reasoning models that reject `temperature` are retried without it (like `think`). `models()` strips Gemini's `models/` prefix and filters out non-chat models; the list is only a suggestion.
- Tool call `id` and `extra` (data the provider requires back verbatim, such as Gemini 3's thought signature, `extra_content` on the OpenAI-compatible endpoint) are stored in `ToolCall`; `loop.ts` writes them into the assistant message and tool messages carry `tool_call_id`. The Ollama client strips them before sending (`toOllamaMessage`; the result is deterministic, so the prompt cache isn't affected). Providers without ids get stable ids by position.
- API keys aren't in `LlmSettings` (settings are sent to the renderer): `secrets.ts` encrypts them with Electron `safeStorage` and stores them in `llmKeys` in `settings.json`, loading them on first use (it must be after app ready). On Linux with `basic_text` (no keyring) they are still saved but `keyEncrypted = false` and the dialog warns; when encryption is unavailable entirely, keys are kept in memory only. A failed decryption counts as no key. IPC `llm.setApiKey` is write-only; keys may only contain visible ASCII, up to 500 characters (they go into a header). Custom addresses must be https or loopback http, so keys are never sent in plain text to another machine.
- `LlmService` state is split into Ollama (`ollamaOnline`, used for embeddings and query vectors) and the cloud (`checkCloud`, which checks the key and connection with `models()`, timing out after 5 seconds). `LlmStatus.online` now means "the current chat provider is available"; in cloud mode, Ollama problems go into `embedError` (a notice that doesn't block chat), and downloading an Ollama chat model is no longer required. A bad key isn't retried; unreachable or timed-out providers are retried every 30 seconds; other errors (for example a provider without `/models`) count as available with no model list. If settings change mid-check, an incrementing sequence number discards the stale result. `num_ctx` is only sent to Ollama. The character budgets were originally tuned for Ollama on a CPU and not relaxed per provider; they now scale with the user's context length setting (see "Context length and max output" below).
- Renderer: AI settings start with the Chat provider choice; for cloud providers they show the API key (a password field showing only "Saved" once stored, with Remove), the Model (`datalist`; the list belongs only to the saved provider) and, for Custom, the API address; switching to a cloud provider requires the consent checkbox before saving. If a key is entered without a model, the dialog stays open after saving so the user can pick from the newly loaded list. The status shows "AI ready · OpenAI"; Indexing isn't shown while Ollama is offline.
- Tested (Ollama's `/v1` endpoint as custom, qwen3.5:2b): streaming, listing models and a two-step Agent tool call (id round trip) all work. Thinking models put their reasoning in `delta.reasoning` on the OpenAI-compatible endpoint, which the client doesn't show; the 2B model occasionally spends the whole last turn thinking and returns an empty answer (the same model behavior as in Ollama mode).

### Context length and max output (2026-11-26)

For the plan and decisions, see `docs/plans/configurable-llm-limits.md`. User decisions: the context setting controls both Ollama's `num_ctx` and the character budgets sent to the model; Ollama and the cloud each have their own pair (`LlmSettings.ollamaLimits` and `cloudLimits`, the latter shared by the three cloud providers).

- `ChatLimits = { contextTokens, maxOutputTokens }`, defaulting to 8192 / `null` (model default). Ranges are in `CHAT_LIMITS` (`shared/llm.ts`): context 2048–1048576, output 256–131072; `cleanChatLimits` rounds to integers and clamps to the bounds, and Ollama's output limit can't exceed the context (`num_predict` also uses context). Old `settings.json` files without these pairs get the defaults. The dialog uses `min`/`max` on `<input type=number>` so the browser blocks out-of-range values, and main checks again.
- Character budgets (`chatBudget` in `main/llm/budget.ts`): Q&A sources and per-chunk limit, the direct/split thresholds for summaries, the agent's total and per-result tool budgets, and the `get_note` page size are all multiplied by `contextTokens / 8192`. The original constants remain as the 8192 baseline, and `chatBudget(8192)` equals them item by item (locked by a test), so default behavior is unchanged. Not scaled: the number of Q&A sources (8, so Q&A text stays bounded even with a very large context), conversation history, and agent steps.
- Summaries, Q&A and the agent still share one setting (`LlmService.chatOptions`), so switching features doesn't reload the Ollama model; the first call after a settings change reloads it once.
- Max output: Ollama gets `options.num_predict`; OpenAI gets `max_completion_tokens` (newer models reject `max_tokens`), and Gemini and custom get `max_tokens` (`OpenAiCompatibleOptions.maxTokensParam`). On a 400 whose error mentions one of the names, the request is resent once with the other name; this is combined with the temperature retry, each parameter adjusted at most once. If both names are rejected, the first error is reported (usually the value exceeds the model's limit).
- Truncation notice: the clients call `ChatOptions.onTruncated` on Ollama's `done_reason: 'length'` and the OpenAI-compatible `finish_reason: 'length'`. The service only looks at the **last** call of each request (the combine step of a split summary, the agent's final answer; truncated intermediate parts and tool-call steps get no notice) and appends an italic line at the end of the stream (`TRUNCATED_NOTICE` in `ask.ts`, in the answer's language). It uses the existing `delta`, so the contract is unchanged; `historyMessages` strips the notice before sending old answers. Tested (Ollama 0.40, qwen3.5:2b): both the native API and `/v1` report `length`; on `/v1`, thinking models can spend the whole limit on reasoning and return an empty answer (the setting's help text warns about this).

## Q&A (phase 6)

For the plan and decisions, see `docs/plans/phase6-rag.md`.

- `llm.ask(req)` returns a request id, and chunks are pushed with `llm:answer` (the same pattern as summaries; cancelling also uses `llm.cancel`). The first chunk carries `sources`, the `range` actually applied and `vector`; the final `done` carries `cited`, the numbers actually cited in the answer.
- Flow (`src/main/llm/ask.ts`): parse the time range → decide the keywords and vector query (`planQuery`) → `retrieve` (top 8 notes) → take each note's most relevant chunk, then add neighboring chunks round-robin by rank, about 8000 characters in total (`gatherSources`) → prompt with numbered sources → filter while streaming.
- Full-text search uses keywords ORed together: Chinese questions have no spaces, so the AND whole-sentence matching in `searchNotes` would never hit. `keywords()` removes punctuation, question words, function words and ordinals such as 「第二點」 ("the second point"); `retrieve()`'s internal `keywords` parameter searches each keyword separately and ranks notes that match more of them higher (sidebar search is still AND).
- When there's only a time and no keywords (「上個月寫了什麼？」, "What did I write last month?"), or retrieval is empty but there is a time range, it lists the notes in the range instead (newest first). When no sources are found at all, it replies with fixed text without calling the model.
- Time range parsing is the pure function `src/shared/timeRange.ts` (shared by main and renderer; the renderer shows the detected range live while typing): today/yesterday, this week/last week (weeks start on Monday), this month/last month, this year/last year, the last N days/weeks/months, `YYYY-MM`, dates and date ranges, months without a year (the most recent one), in Chinese and the English equivalents. Only the first phrase is used, and it is removed from the retrieval query. `AskRequest.range`: `undefined` lets main parse it, `null` disables filtering, and a value is used as is.
- Citation format `[n]`: maps to a passage (path + line number), and clicking scrolls to that line. `createCitationFilter` normalizes `[1, 2]` and `【1】` into `[1][2]` and drops out-of-range numbers; `createLinkFilter` then keeps only wikilinks that appear in the sources and the source titles.
- The answer language follows the question (Traditional Chinese when CJK characters ≥ English words); in English, the language instruction is repeated after the content. Multi-turn conversations include the last 3 rounds (6 messages, each cut to 1000 characters), with `[n]` stripped from old answers (they referred to earlier sources). For follow-ups (no keywords or phrased like a follow-up), the vector query adds the previous question.
- Renderer: a "Chat / Summary" toggle at the top of the AI tab (`knowmon.ai.mode`); `Ctrl/Cmd+Shift+A` opens the chat and focuses the input; `Ctrl/Cmd+Shift+S` switches to Summary. Conversation state is pure (`renderer/chat/conversation.ts`), kept only in the app's memory and cleared when switching vaults. The `citations` option of the `Markdown` component parses `[n]` as citations (a lezer inline extension placed before Link, so `[1][2]` isn't taken as a reference link). Copying an answer replaces `[n]` with `[[source title]]`. Enter during IME composition doesn't send.

## Agent (phase 7)

For the plan and decisions, see `docs/plans/phase7-agent.md`. The code is in `src/main/llm/agent/`.

- Uses Ollama's native tool calling (`/api/chat` with `tools`). `OllamaClient.chatTools` returns text and `tool_calls` (string `arguments` are parsed as JSON first); when a model doesn't support tools (`does not support tools`), it reports a clear error asking the user to change models in Settings. Summaries, Q&A and the agent all send the same `num_ctx` (8192 by default, configurable in AI settings; see "Context length and max output"): Ollama's default of 4096 cuts off the beginning, and a different `num_ctx` reloads the model and clears the prompt cache (2026-10-19).
- The loop (`runAgent` in `loop.ts`; chat, tools and confirmation are all injected by the caller): the model replies with tool calls → they run in order → results are added back with `role: 'tool'` → next step, until the model answers directly. At most 5 tool calls; after that, tools are no longer offered and the model is asked to answer. Repeated calls with the same tool and arguments (in any order) aren't executed; tool errors and unknown tools return the error to the model as the result instead of aborting the task. On a CPU, reading a prompt runs at about 17 tokens/s, so the length of tool results directly sets the task time (tuned 2026-10-19, see `docs/plans/phase7-agent.md`): each result is cut to 1500 characters and all results share a 6000-character budget (at context 8192; scaled proportionally to the configured context length); a new result is cut to the remaining budget (at least 300 characters), and once the budget is used up, tools are no longer offered. **Messages already sent are never rewritten**: changing an earlier message invalidates Ollama's prompt cache and the whole conversation is read again. Earlier tasks include only the last 4 messages, 600 characters each.
- Tools (`tools.ts`) return compact plain text (not JSON), one line per note: "title | path | date". Path arguments also accept a title or `[[title]]` (the rules in `shared/links.ts`). Time ranges come from the `period` argument parsed by `parseTimeRange`; **the model never converts dates itself** (in testing, qwen3:8b got 「上週」 "last week" off by a day and only gave `from`); time phrases written in `query` are extracted too. `search_notes` reuses Q&A's keyword-OR + vector retrieval. `get_note` reads the file with `Vault.peek` and **records no `open` event** (the user didn't open it); long notes are paged with `offset` (1200 characters per page). `search_notes` defaults to 5 notes (max 10) and `list_notes_in_range` to 10 (max 15), with an 80-character snippet each. `get_neighbors` first runs `await vault.graph()` so time and semantic edges are current, groups by type, and lists link targets that don't exist yet.
- Write tools only produce proposals (`AgentStep.status = 'confirm'` with a `proposal`); `LlmService` waits for `llm.confirm` keyed by `${request id}:${step}`. Stopping, switching vaults or closing the app counts as rejecting a pending proposal. Users can edit proposals (the path and content of `create_note`, removing individual tags from `add_tags`); IPC only takes those fields and keeps the rest of main's original proposal.
  - `create_note` uses `Vault.create(path, content)` (`wx`, never overwrites; with content it records `create` and `edit`). `.md` is appended to the path, and `normalizeRel` rejects `..` and hidden folders.
  - `add_tags` uses `Vault.update(path, f)`: it rereads the file in the queue, applies the change and writes it back, so edits the user made while the confirmation was pending aren't overwritten. After writing it pushes `vault:changed` (`change`), and open tabs handle it like an external change (reload if there are no unsaved edits).
- Tags are written to `tags:` in the frontmatter (user decision, 2026-10-18). `addTags` (`tags.ts`, pure) only changes the `tags` lines: flow lists get the tag before `]`, block lists get it after the existing items with the same indentation, a single string or multi-line flow list is rewritten as `tags: [...]`, a missing `tags` is added before the closing `---`, and a missing frontmatter is created at the top; CRLF is preserved. Existing tags are compared case-insensitively, ignoring `#`; corrupt YAML is not modified.
- The final answer goes through `createLinkFilter`, keeping only note titles from tool results and links in the text that was read. The system prompt includes today's date and weekday, and the language follows the task (`detectLanguage`). Multi-turn history includes only earlier tasks and final answers (not the tool steps).
- Renderer: the top of the AI tab became "Chat / Agent / Summary" (user decision to keep Chat, 2026-10-18; `knowmon.ai.mode` gained `agent`); `Ctrl/Cmd+Shift+G` opens the Agent and focuses the input. Task state is pure (`renderer/chat/agentRun.ts`): text and steps are ordered by arrival, and a step with the same index replaces the earlier one; text after the last step is the final answer, and earlier text is shown faded. While waiting for confirmation, the Agent button, the AI tab and the status at the bottom of the sidebar all show a reminder. Kept in memory only and cleared when switching vaults.

## Workspace: tabs and panels

For the plan and decisions, see `docs/plans/workspace-tabs.md`.

- Tab state is pure (`src/renderer/src/workspace/tabs.ts`): a tab is a note, the graph or the timeline; each note opens in at most one tab (opening it again switches to it), and there is at most one graph tab and one timeline tab.
- Choosing a note (file tree, search, backlinks, graph, Quick switcher) **replaces the current tab** by default; `Ctrl/Cmd+click` or middle-click opens a new tab (user decision, 2026-10-07). New notes open in a new tab. There is no back/forward.
- Replacing a tab gives it a new id; views are keyed by tab id, so switching notes rebuilds the editor, while renaming (`renamePaths`) keeps the id and the editor (cursor and undo are unaffected).
- Each note tab (`NotePane`) has its own CodeMirror and reads its file only when first shown (so restoring many tabs doesn't read every file at once or record an `open` event for each), then stays mounted and hidden. Each tab handles external changes itself; external deletions close the affected tabs from App.
- Autosave is still a single `createAutosave`: only the current tab receives input at any time, and editing another note writes out the previous one first; replacing or closing a tab also flushes.
- Tabs are stored in the renderer's localStorage (`knowmon.tabs:<vault path>`), one entry per vault; notes that no longer exist are skipped on restore. Nothing is saved until restoring finishes, so an empty state can't overwrite the previous tabs.
- Electron's default menu binds `Ctrl/Cmd+W` to closing the window; the main process uses a custom menu instead (`buildMenu` in `src/main/index.ts`) without it, and the renderer uses the shortcut to close tabs.
- Panels: the left sidebar and the right panel can be resized by dragging (`Splitter`; double-click restores the default), within limits that leave the editor at least `EDITOR_MIN` (`workspace/layout.ts`). `Ctrl/Cmd+B`, `Ctrl/Cmd+Alt+B` or the buttons at both ends of the tab bar toggle the left and right panels. Widths and visibility are stored in localStorage `knowmon.layout`, shared by all vaults.
- Global shortcuts are intercepted in `App.tsx` in the capture phase with `stopPropagation`, so the editor doesn't handle the same key again (which disables CodeMirror's `Ctrl/Cmd+G` "find next"; use `F3` instead). The full list of shortcuts is in the user guide at `docs/user-guide/shortcuts.md`; update it when adding or changing a shortcut.
- Shortcuts: `Ctrl/Cmd+W` closes a tab, `Ctrl+Tab` / `Ctrl+Shift+Tab` switch tabs, `Ctrl/Cmd+T` opens the Quick switcher in a new tab (`Ctrl/Cmd+Enter` in the Quick switcher also opens a new tab), `Ctrl/Cmd+G` opens the graph tab, `Ctrl/Cmd+Shift+T` the timeline tab.

## Images

- Notes support only the standard syntax `![alt](relative path)`, with paths relative to the note's folder (user decision, 2026-10-20); URLs, absolute paths, paths leaving the vault and hidden files aren't rendered. Both `<a b.png>` and `%20` are recognized. The rules are the pure functions in `src/shared/assets.ts` (shared by main and renderer). `![[x]]` isn't supported (the Markdown parser sees an Image without a URL, so it's unaffected and still handled as a wikilink).
- Display: main registers the privileged protocol `knowmon-asset://vault/<path>` (`src/main/index.ts`, handler in `src/main/vault/assets.ts`), which serves only image files inside the current vault, with `normalizeRel` blocking `..` and hidden folders. The CSP's `img-src` includes `knowmon-asset:`.
- Live rendering (`ImageWidget` in `renderer/editor/images.ts`): when the cursor isn't on the image syntax, it is replaced by the image; when it is, the image follows the raw syntax. The note path is passed in through the `notePath` facet and reconfigured on rename without rebuilding the editor. `requestMeasure()` runs after the image loads. Source mode shows no images.
- Pasting or dropping images: saved to `attachments/` at the vault root (`notes.saveAttachment`, added to the contract with the user's approval, 2026-10-20), with a number added on a name clash (`wx`, never overwrites), up to 50 MB per file. Clipboard screenshots (always named `image.png` by Chromium) are renamed to `Pasted image YYYYMMDDHHmmss.png`; dropped files keep their names (minus invalid characters, `%` and `#`). The inserted path is relative to the note and wrapped in `<>` when it contains spaces or parentheses. When the clipboard also has text, it's pasted as ordinary text. Users may move images afterwards, but must update paths in their notes themselves.
- Images aren't stored in the DB and have no events; the file tree still lists only `.md` files (the `attachments` folder itself is shown).

## Renderer

- Autosave: writes 500 ms after typing stops; `Ctrl/Cmd+S` writes immediately. It flushes before replacing or closing a tab, renaming, deleting or switching vaults.
- An open note (any loaded tab) changed externally: reloads directly if there are no unsaved edits; otherwise a bar in that tab lets the user choose.
- New note/folder: a name field appears in the file tree first, and the item is created on Enter (or blur), instead of creating `Untitled` and renaming it (the new note tab's editor grabs focus once loaded, which broke the rename field). Duplicate names (case-insensitive) are blocked in the renderer first (`newItemPath` in `lib/tree.ts`). The name field ignores Enter during IME composition.
- Drag-and-drop moves in the file tree use `notes.rename(from, to)` directly, with no extra IPC. Drag data uses a custom MIME type, `application/x-knowmon-path`, to tell it apart from files dragged in from the system.
- Live Markdown rendering (`src/renderer/editor/livePreview.ts`): implemented with CodeMirror decorations, never changing the document. Inline elements (bold, links, code, wikilinks) show raw syntax when the cursor touches them; block marks (heading #, quote >, lists, horizontal rules) show on the cursor's line. `Ctrl/Cmd+E` or the button at the top right toggles source mode, stored in the renderer's localStorage.
- Frontmatter is detected with a regex for the `---` block at the start of the document rather than a lezer grammar extension (an unclosed `---` would swallow the whole document). Wikilinks are also found by regex, excluding those in code; lezer treats `[x]` inside `[[x]]` as a Link, so Links that overlap a wikilink or have no URL aren't rendered.
- Code blocks: when the cursor is outside a block, the ``` fences are hidden and only the language is shown at the top right (fence lines keep their height so line numbers stay aligned). Syntax highlighting uses `@codemirror/language-data` (added with the user's approval, 2026-10-06), whose language packages load dynamically only when a note uses them; unknown languages are shown as plain text.
- Tables (`src/renderer/editor/tables.ts`, plan in `docs/plans/table-rendering.md`): when neither the cursor nor the selection is in a table, the whole table (full lines) is replaced by a `<table>` widget; as soon as it's touched, the whole table shows its raw Markdown, with no in-cell editing (user decision, 2026-11-11). Clicking a cell puts the cursor in that cell's source (the widget records offsets from the start of the table's line and adds `posAtDOM` on click); clicking the scrollbar or empty space doesn't expand it. Replace decorations spanning line breaks can't come from a ViewPlugin, so tables use a separate StateField (part of `livePreview()`, disabled in source mode), and `buildDecorations` skips replaced tables. Only tables at the top level of the Document are rendered; those in quotes and lists aren't (replacing whole lines would eat the `>` and list markers). Inline styles in cells become spans following the syntax tree (bold, italic, strikethrough, code, links, wikilinks, `\|`), built with DOM APIs; a wikilink's display text in a cell must be written `[[x\|y]]` (in GFM a `|` always separates columns), and on the indexing side `wikilinkTarget` (`shared/links.ts`) also treats `\|` as the display-text separator. Wide tables use `contain: inline-size` so their frame scrolls horizontally without widening `.cm-content`.
- Math (LaTeX), plan in `docs/plans/latex-rendering.md` (user decision, 2026-11-25: KaTeX; `$…$` / `$$…$$` in notes; AI replies also accept `\(…\)` / `\[…\]`): the syntax is a lezer Markdown extension (`editor/mathSyntax.ts`, nodes `InlineMath` / `BlockMath` / `MathMark`), shared by the editor and `chat/parseMarkdown.ts`, so code spans and `\$` take precedence normally. Inline `$`: the opener isn't followed by whitespace; only the first unescaped `$` after it can close, and it must not be preceded by whitespace or followed by a digit (`$5 and $10` stays text), one line only. A block starts at a line beginning with `$$` (it can interrupt a paragraph) and closes at the first line ending with `$$`; `$$a$$ and $$b$$` on one line is inline math. A blank line or the end of the enclosing quote/list ends an unclosed block, and unclosed blocks are never rendered, so a stray `$$` only swallows lines up to the next blank line. The block parser reads lezer's untyped `Line.depth` (as FencedCode does) to stop at the end of a container. KaTeX runs in `editor/mathRender.ts` with `trust: false` (no `\href`, `\includegraphics` etc.), `strict: 'ignore'` (CJK text in math) and `throwOnError` (errors show the raw TeX in red, message as tooltip). `katex.render` builds DOM nodes, never an HTML string; results are cached (500 entries) and cloned. Inline math is a replace widget in the ViewPlugin (source while the cursor touches it). Blocks are a StateField (`editor/math.ts`) like tables: top-level blocks become a block widget over whole lines; blocks in quotes/lists become an inline widget from the opening `$$` to the end of the closing line, so the container markers stay; with the cursor inside, the source is shown with a rendered preview below. Wikilinks inside math aren't decorated. Inline math in table cells becomes a `math` span (`\|` → `|`). In AI replies an unclosed block (streaming) is shown as raw text; `Markdown.tsx` renders formulas into a ref with `useLayoutEffect`. KaTeX's CSS is imported in `main.tsx`; its fonts are bundled by Vite and allowed by the CSP's `default-src 'self'`.
- External links need `Ctrl/Cmd+click`, only allow http(s) and mailto, and are handed to the system browser through `setWindowOpenHandler` in the main process.
- The font list must name `Noto Sans CJK TC` explicitly: a full-width punctuation mark that ends up as its own text node (common when hidden marks split the text) gets a narrow glyph if left to the system fallback.
- Themes: light (off-white) and dark (a darker background than Nord, with Nord code colors). Every color is a CSS variable in `main.css`; the dark versions are defined under `:root[data-theme='dark']`, and syntax colors use `--hl-*` variables, so `livePreview.ts` doesn't need to know the current theme. The choice is stored in the renderer's localStorage (`knowmon.theme`) and applied before React's first render to avoid a flash.
- IPC channel names are centralized in `src/shared/channels.ts`.
- Icons and logo (plan in `docs/plans/ui-logo-icons.md`, 2026-11-13): all UI icons are hand-written inline SVGs in `src/renderer/src/components/icons.tsx` (24×24, `currentColor`, stroke width 1.8), with no icon package; add new icons there. The logo is "a K made of connected nodes, with an outer ring of dotted time marks" on a dark background (chosen by the user), with fixed colors that don't follow the theme; in the dark theme a thin `box-shadow` border separates it from the background. The renderer's `Logo` component is an inline SVG (solid background, no gradients, so multiple instances don't clash on ids), and the CSP needs no change.
- The app icon's source is `build/icon.svg`; `node scripts/gen-icons.mjs` uses the system ImageMagick (`magick`) to produce `build/icon.png` (1024), `build/icon.ico` and `resources/icon.png` (512, the Linux window icon), and `scripts/icns.mjs` assembles the `.icns` directly (no need for macOS's `iconutil`). The generated files are committed, so packaging doesn't need ImageMagick.
- Left sidebar: Files/Search are tabs that switch the sidebar's content (icon + text); Graph/Timeline/Quick switcher are actions that open tabs and show only icons (the tooltip has the name and shortcut). `.sidebar` and `.side-panel` set `container-type: inline-size`, and when they're too narrow (sidebar ≤ 240px, right panel ≤ 290px) the tab text is hidden with `@container`, with buttons keeping their `aria-label`.
- Settings entry: the gear at the bottom left of the sidebar (`components/SettingsMenu.tsx`) opens a menu for the two existing dialogs (Time & links, AI); they haven't been merged (a combined settings page is a separate, still undecided roadmap task). The AI item is disabled until the AI status has loaded, because `LlmSettingsDialog` needs the current settings. The existing Settings buttons in the graph, timeline and AI tabs remain, now with a gear icon.

## Development environment notes

- better-sqlite3 13 ships N-API prebuilds, so the same binary works in Node (vitest) and Electron without a rebuild.
- sqlite-vec is loaded by `openDb` (the `.so` in `node_modules/sqlite-vec-<platform>`); if loading fails, vector features are disabled and the AI status shows why. SQLite reads the file directly with `dlopen`, bypassing Electron's asar redirection, so packaging unpacks `node_modules/sqlite-vec-*` with `asarUnpack` and the load path goes through `unpackedPath` to `app.asar.unpacked` (phase 8, see `docs/plans/phase8-packaging.md`). Only the `sqlite-vec-<platform>` for the build machine's platform gets installed, so installers must be built on their own operating system.
- userData is fixed to `<appData>/knowmon` (`app.setPath` at the top of `src/main/index.ts`): by default it follows productName, which would be `Knowmon` in the packaged app and separate its settings and localStorage from the development build (user decision, 2026-10-20).
- File names must not differ only in case (macOS/Windows are case-insensitive, so imports would resolve to the wrong file): `scripts/case-collisions.test.mjs` checks the whole repo, and CI also runs `electron-vite build` on all three platforms.
- Installers are built per platform by GitHub Actions (`.github/workflows/release.yml`: pushing a `v*` tag creates a draft Release, which the user checks and publishes by hand; `workflow_dispatch` only does trial packaging); `ci.yml` runs vitest on three platforms on pushes to main and on PRs, plus typecheck and lint on Linux. Linux installers are built on `ubuntu-22.04` to avoid too new a glibc. electron-builder's `--publish` isn't used (it generates auto-update metadata, which conflicts with `publish: null`); `gh release create` is used instead. Version 0.1.0, MIT license (user decision, 2026-11-15). Process in `docs/releasing.md`.
- `.gitattributes` forces LF (`* text=auto eol=lf`): git on Windows converts to CRLF by default, which affects Prettier and tests that read file contents.
- Packaging configuration (`electron-builder.yml`): Linux produces AppImage, deb and rpm (originally only the first two, user decision 2026-10-20; rpm added for Fedora-family systems 2026-11-15); Windows uses NSIS; macOS produces only dmg, with the arch in the file name (`${name}-${version}-${arch}`, otherwise arm64 and x64 overwrite each other). There is no Apple certificate on macOS, so `mac.identity: '-'` gives an ad-hoc signature (Apple Silicon won't run apps without a valid signature) and `hardenedRuntime` is off (only notarization needs it; ad-hoc signing with library validation blocks sqlite-vec's dylib); `publish: null`, so no auto-update. The AppImage uses `toolsets.appimage: '1.0.3'` (static runtime, beta): the old runtime needs libfuse2, which Ubuntu no longer installs by default after 22.04, causing `error loading libfuse.so.2` at startup; the new runtime's AppRun adds `--no-sandbox` automatically when user namespaces are unavailable (AppArmor on Ubuntu 24+). `desktopName` in `package.json` and `linux.syncDesktopName` map the Wayland window to `knowmon.desktop`.
- Cytoscape's canvas takes its height in whole pixels, so a container with a fractional height overflows by 1px; `.graph-canvas` therefore sets `overflow: hidden` (a wrapping toolbar once gave the whole page a scrollbar).
- chokidar 5 is ESM-only, so `electron.vite.config.ts` bundles it into main instead of treating it as external.
- `npx tsc --noEmit` with the root project references checks no files; use `npm run typecheck` for type checking.
- The README screenshots are `docs/images/screenshot-{light,dark}.png` (1280×800; the README switches by the reader's theme with `<picture>`). Retake them after UI changes: use the built app with `XDG_CONFIG_HOME` pointing to a temporary folder (so your own settings aren't touched) and a copy of test-vault (only test notes in the shot), collapse every folder except Books, open "Deep Work" with the right panel on Local graph at depth 1 and wait for "AI ready" (so semantic edges are drawn), one light and one dark. Name the vault copy "Sample vault", since the folder name is the sidebar title, and start Electron with `--force-device-scale-factor=1` on a HiDPI screen; `docs/` isn't packaged.
- Language (2026-11-26, user decision; plan in `docs/plans/english-translation.md`): documentation, plans, code comments and test titles are in English. Chinese appears only where it's functional: zh-TW prompts and notices, Chinese keyword/stopword lists and time phrases, test inputs and expected outputs, and `test-vault/`.
